## Findings

### P2 — stale observed worker could falsely prove all coaching disabled — resolved and independently retested

Original `src/server/observability/worker-attestation.ts:33–65` parses only fresh instances, then calculates `allKnown`, matching builds and `allCoachingDisabled` from that subset. One fresh safe worker plus an observed worker whose last autonomous-enabled heartbeat is 121 seconds old returns `allCoachingDisabled: true`; the source also calculates ready/ok true. A stale heartbeat does not establish that a process stopped sending. This conflicts with the incident runbook's explicit stale/unknown caveat.

Independent desired-behavior regression added to `qa/pilot-2026-10-22/independent-platform-probe.test.ts`: fresh safe + stale enabled instance must not prove all coaching disabled. It **failed before repair** because the actual value was true. The existing STOP regression in that probe still passed. Root and the R2 author were notified; this reviewer did not modify the product.

Required acceptance: stale/future/malformed or unretired legacy evidence cannot make a known-policy/all-disabled claim. Retain observed unknown lifecycle evidence rather than silently aging it out of the reader or deleting it on a timer. Fresh worker availability can be reported separately if the operator safety verdict stays unknown/false. Instance retirement must follow independently established shutdown; heartbeats are not an authoritative deployment inventory.

The R2 author repaired the calculation and lifecycle. Policy knowledge now includes all observed unretired evidence; stale/future/overflow evidence forces `policyKnown=false`, `allCoachingDisabled=false` and nullable policy permissions with an explicit problem. Both readers retain old rows without a time cutoff; stale rows are no longer automatically deleted. Root explicitly approved separating active availability from a proof that all observed coaching is disabled, so active readiness may remain true while the operator safety verdict stays unknown. The independent regression asserts that safety contract, not an unrelated requirement to withdraw active availability.

Independent rerun expanded the probe to 121-second, 601-second and eight-day stale instances: **all three safety cases passed**. The existing STOP regression also passed. The final nearest R2 selection passed **39 tests / seven files**, including old-row retention, legacy/future/overflow handling, read-only reporting and heartbeat lifecycle. No unresolved P1/P2 finding remains in this reviewed package.

### P3 — asynchronous heartbeat retirement race — addressed; delayed-write tests passed

The earlier `src/worker/runtime.ts` started interval callbacks with `void heartbeat()` and cleared the interval during shutdown. Clearing an interval does not await a heartbeat already in progress. If its database work finished after `removeWorkerHeartbeat`, it could recreate the retired row before pool shutdown finished, producing lingering unknown lifecycle evidence. This was a source-backed availability/cleanup concern, not a reproduced sending bypass.

The author introduced `src/worker/heartbeat-lifecycle.ts` to serialize pulses, stop new pulses and join the outstanding write before retirement. Runtime retires only its exact instance after pg-boss stop and an empty application-worker list; timeouts with unwinding handlers retain evidence. The installed pg-boss source was checked: `getWipData()` retains non-stopped application loops, including stopping loops, so this check matches the local SDK semantics. Independently executed lifecycle tests hold/release an in-flight write and reject failed writes; no later pulse can recreate the retired row. Both tests passed in the final R2 selection.

No blocking A2 authorization, confidentiality, idempotency, deletion or timezone-consent-side-effect defect was identified in the inspected source and passing nearest tests.

## A2 acceptance evidence

Account IDs, transcripts and attachments cannot be supplied as extra fields. Repository submission rechecks a persisted verified non-deleted account under row lock; receipt lookup scopes both account and report ID. There is no customer report-list/detail API.
- **Encrypted storage and logging:** `pilot-feedback-repository.ts` uses the existing random-IV AES-256-GCM field encryption for optional detail and keyed HMAC for retry payload identity. Ordinary output does not decrypt detail. API unexpected-error logs omit the exception object, SQL/input and detail. Integration tests assert absent plaintext, successful explicit decryption and no created conversation/job rows.
- **Retries and cap:** account lock plus `(user_id, request_id)` uniqueness serializes retries. Lookup precedes cap consumption; identical retries return the original receipt even at the cap, changed content conflicts, and the other account cannot inherit a receipt. Five new reports per fixed hour are enforced by durable buckets. This is a fixed-window cap, not a rolling hour or global abuse budget.
- **Deletion:** additive migration `0032_pilot_feedback.sql` uses an account FK with ON DELETE CASCADE. The integration test invokes the ordinary account-control delete path, verifies report/receipt removal and preserves the other account's reports. A deleted/unverified account cannot submit.
- **Operator disclosure:** `scripts/pilot-feedback-report.ts` defaults to bounded metadata with a keyed account pseudonym, never phones/chats. `--details` requires one explicit UUID; it intentionally reveals only that report's submitted note. There are no send or mutation calls. The CLI loads configured environment files for its explicit operator purpose; it was not executed against configured data by this reviewer. Follow-up consent is stored, not acted upon automatically; human triage ownership remains an operating requirement.
- **Timezone:** strict setup action accepts named supported IANA zones/UTC and rejects raw offsets, unknown zones and authority-bearing extra fields. The server updates only the shared account zone, confirmation timestamp and updatedAt while preserving other preferences. Existing reminder instants/timezones, consent, opt-in, quiet hours and onboarding state stay unchanged. Integration coverage rereads actual inbound orchestration context with the new zone and asserts zero consent/jobs. The device suggestion fills a field only; confirmation issues the save. Current `saveSetup` throws on a competing mutation rather than resolving a no-op as success. Browser focus/failure retention remain root's checks.
