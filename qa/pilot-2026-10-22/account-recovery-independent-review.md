## Evidence and behavior

`npm run test -- src/app/components/account-state.test.ts src/app/components/account-resource.test.ts src/app/components/account-recovery-views.test.ts src/app/profile/profile-owner-submit.test.ts src/server/security/public-account.test.ts src/server/security/authenticated-route-errors.test.ts` passed **6 files / 36 tests** (exit 0).

- The profile PUT authenticates the cookie, requires verified status, validates the body, and compares `expectedCacheKey` against the authenticated user's discriminator before `updateProfile`. Missing/mismatched keys return 409 without calling the mutation. Client owner-change handling discards the editor and invalidates the account projection; a new owner gets a newly keyed editor. The opaque discriminator is a stable hash of the UUID, not a credential or editable display/phone identity.
- Same-owner poll object replacement preserves keyed editor/projection identity; a changed key remounts. Board and Extensions GET use authenticated ownership rather than request-supplied IDs and return that owner's key. `resourceSuccess` drops a mismatched response rather than displaying the other owner's payload. Explicit account events immediately invalidate cached ownership, while aborted/superseded/body-late responses are ignored.
- Temporary failures retain only a previously verified same-owner projection, visibly labeled as last known/stale. Profile save is disabled, extension action links are removed, and stale spoken board briefings are disabled/cancelled. Fresh empty/error states are distinct from disconnected/setup-incomplete claims. Resource 401/403 clears its private projection; account polling 401/403 or successful `{account:null}` clears account identity.
- Pending-verification public accounts retain the existing phone suffix/setup status only; they expose no new cache discriminator, display name, instructions, calendar status or profile-complete assertion. Routes use private/no-store responses and operation-only error logs without query/credential/content diagnostics. The route suite verifies these boundaries with synthetic errors.

## Narrow finding corrected and independently verified

The initial `ProfileClient.tsx` save handler treated only 409 as an immediate owner invalidation. An explicit PUT 401, returned by the server for missing/unverified sessions, only displayed an error; the private editor/draft stayed mounted until the next six-second account poll detected auth loss. Root coordinated the author repair. It was bounded UI retention, not a cross-account write or authentication bypass; the server rejected the write.

The final handler now processes 401 and 409 **before parsing any response body**. A 401 invalidates the shared account projection and unmounts the editor into a login gate; a 409 unmounts into its separate owner/reload gate. A 403 origin rejection retains the draft rather than claiming auth loss. The expanded form test uses deliberately non-JSON bodies for both 401/409 and verifies the emitted account event, correct recovery state, absence of the private draft/form and login link for 401. Independent rerun: `npm run test -- src/app/profile/profile-owner-submit.test.ts src/app/components/account-recovery-views.test.ts src/app/components/account-state.test.ts` passed **3 files / 13 tests**, exit 0. The finding is closed; no remaining actionable finding was identified in this reviewed subset.

## Core workspace/setup/feedback follow-up review

Independently reviewed the final separately authored `WorkspaceClient`, `workspace-data`, `PilotFeedback`, `feedback-submission`, workspace/setup/feedback routes and tests, authenticated-route error fixture, mutation retry tests, and the three changed existing HTTP QA helpers. No production source was edited by this reviewer.

Workspace/setup/feedback mutations authenticate the cookie and require the rendered owner's `x-tempo-account` header to match the server-derived key before mutation. Workspace/setup check it before consuming their write limiter; feedback checks it before entering repository submission (which owns its limiter). Missing and stale keys fail with 409/account_changed. The server, not the submitted header, selects the account. Successful responses echo that authenticated owner. Tests cover old drafts after a synthetic cookie/account change, no mutation/limiter call on mismatch, and valid current-owner writes. Public read responses and feedback receipts include an owner key; client mismatches invalidate instead of reconciling private data or claiming a receipt.

The entire stateful `WorkspaceView` is keyed by the verified immutable owner, containing editor, routine editor, setup dialog, chat draft, undo state, mutation tracker and feedback dialog/retry identity. Same-owner account polls and transient account errors preserve that component; account invalidation/unverified status hides it, and another key remounts it. Late mutation/feedback results check mounted status; workspace reads use request sequencing, including a second check after body resolution. Transient read/account failures retain the prior snapshot while mutation/setup/feedback submission guards refuse writes. Preview has a separate key, no owner requirement, local synthetic mutations and disabled feedback submission. The changed historical HTTP helpers now carry a key from an authenticated read before writing; they were inspected, not rerun, in this review.

A further confirmed auth-loss gap was corrected during review: workspace refresh, workspace action, setup save and feedback submission initially parsed JSON before processing a confirmed 401. The author moved 401 handling ahead of body parsing in all four paths. Final direct workspace-refresh and feedback tests use malformed 401 bodies to verify immediate invalidation without reading JSON. New direct refresh-callback tests also verify cross-owner snapshot rejection, same-owner 503 retention/success reconciliation, and late superseded body rejection. Existing retry tests verify uncertain mutation identity preservation; feedback tests bind the owner header and retry identity, reject cross-owner receipts and change request IDs across owners.
