# R2 worker attestation and operational report — 2026-10-22

## Result and interfaces

Implemented bounded per-instance worker build/policy attestations and an operator-only aggregate report. No schema migration, deployment configuration change, service provisioning, production access, provider/model call, purchase, alert installation or commit was performed by this package owner.

- `src/server/observability/worker-attestation.ts` validates versioned heartbeat metadata, queue counts, policy booleans and build stamps. Public summaries select only counts, booleans, validated builds and fixed status/problem codes. Canary targets, worker/account IDs, PID, credentials and arbitrary metadata are never serialized.
- `src/worker/runtime.ts` creates a startup UUID instance heartbeat while retaining the existing `tempo-worker` compatibility record for `demo:report`. Stored policy reflects the running process's cached configuration. It reports independent cleanup permission and the canary override without exposing target IDs.
- Optional `TEMPO_BUILD_SHA` is 7–40 hexadecimal characters. If empty, a valid `RAILWAY_GIT_COMMIT_SHA` is used. Unknown builds remain explicit and do not prove readiness or disabled policy. Matching stamps still require external verification that the intended artifacts were actually deployed.
- `/api/health` preserves existing flag fields, labels them `configurationScope=web` and adds the web build/count. It never claims these are worker settings. `/api/ready` preserves the existing ready-worker contract but requires current valid worker/build/queue evidence. `workerAttestation` separately reports policy confidence and whether disabled coaching was actually proven over observed records.
- `scripts/staging-smoke.ts` now checks worker build equality and the disabled-coaching verdict, including canary/cleanup paths; safe-looking web flags alone are insufficient.
- `npx tsx scripts/pilot-operations-report.ts --hours 24` reads a repeatable-read **READ ONLY** SQL transaction with a five-second statement timeout. It has bounded 1–168-hour reporting windows, fixed queue/action categories, aggregate activation/delivery/backlog/failure/recovery data and constant suggested operator actions. Held work is all-time so older failures cannot disappear outside the reporting window. It never starts pg-boss or initializes its schema. It uses operator-provided process configuration and does not load environment files. Exit 0 is a report without problems, 2 indicates reported problems, and 1 means completion failed.

## Independent findings and corrections

The independent reviewer reproduced a false-safe first draft: one fresh safe worker plus a 121-second-old sending worker could produce `allCoachingDisabled=true`. This was a meaningful correctness defect and was fixed before checkpointing R2.

The final reader includes unretired instance history without a timestamp cutoff and reads at most 22 rows. Fresh runtime availability can remain ready, but any observed stale/future/malformed/legacy evidence or bounded-inventory overflow makes the policy verdict unknown and disabled coaching unproven. Old timestamps never imply termination and are never auto-deleted. More than twenty fresh instances fails active attestation; old unretired rows do not permanently block active availability, but do require review before the stronger policy verdict can become known. Report terminology refers to **observed instances**, not an authoritative deployment inventory. Unknown processes outside those records require external inventory verification.

The reviewer also identified an in-flight heartbeat race during shutdown. `src/worker/heartbeat-lifecycle.ts` now serializes writes, joins the in-flight pulse and prevents late interval writes before retirement. The runtime removes only its exact instance row after pg-boss has stopped and `getWipData()` reports no remaining application worker loops. Local pg-boss source inspection confirms timed-out stopping loops remain observable there. A crash/timeout/unresolved loop retains its record for independently verified operator retirement. A fresh valid compatibility heartbeat is not double-counted as a second worker.

`docs/OPERATIONS.md` now states that global coaching switches do not disable independent cleanup or canary overrides, requested reminders, replies, sign-in or compliance paths. Immediate queued-work halt requires stopping workers; a complete halt of application-triggered provider operations also requires suspending web signup/verification entry points or the web service, since signup can directly request provider verification. Already accepted submissions cannot be recalled. Web liveness cannot prove worker safety. No actual deployment was stopped or changed by this package.
