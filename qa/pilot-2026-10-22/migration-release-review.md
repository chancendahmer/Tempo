## Assessment

The database changes are additive and support an expand-before-code rollout. No destructive migration or required data backfill was found. Resolve the two repository consistency issues below before merge; hosted release approval still requires the deployment and restore evidence in the launch checklist.

1. **0032 foreign-key name differs from schema/snapshot metadata.** The inline `REFERENCES users(id) ON DELETE CASCADE` creates `pilot_feedback_user_id_fkey`, confirmed against the locally migrated database. The Drizzle schema/snapshot expects `pilot_feedback_user_id_users_id_fk`. Runtime cascade works, but a future generated FK change/drop could target a name that is absent. Before 0032 is shipped, explicitly name its FK to match the snapshot, or consistently align the schema/snapshot to the actual name. Do not rewrite a migration that has already been applied to a shared environment; use a follow-up rename migration there.
2. **The deployment guide incorrectly says the worker never migrates.** Both committed Railway configurations run pre-deploy migrations: web runs compiled `dist-ops/scripts/migrate.js`; worker runs `npm run db:migrate`. Both reach `scripts/migrate.ts` and the same session advisory lock. Correct `docs/DEPLOYMENT.md:18` to describe this actual behavior and coordinated web-first rollout. Removing the worker pre-deploy command is a separate operational decision, unnecessary for this release and not performed here.

## Compatibility, atomicity, and deletion

- 0031 adds nullable `tasks.presentation` JSONB, without default/backfill or replacement of an existing field. Existing tasks survive with `NULL`; older deployed code can continue using its existing columns. New workspace queries and presentation-worker queries require 0031 before startup. PostgreSQL still needs a brief table DDL lock; `lock_timeout = '120s'` bounds lock acquisition rather than making deployment lock-free.
- 0032 creates a new table plus indexes and bounded enum-like checks. Existing web/worker code does not reference it. New feedback submission/reporting requires 0032; R2 worker attestation uses the existing heartbeat table and metadata, requiring no additional schema change.
- Journal entries are sequential through idx 32, with 0032 timestamp strictly after 0031. Installed Drizzle reads this journal, applies pending statements and ledger inserts in a transaction, and uses the latest ledger timestamp to skip already applied migrations. Raw SQL is deliberately not individually rerunnable. Keep prior SQL/journal history immutable and deploy the SQL files and journal together.
- `withMigrationLock` holds advisory lock `724651102` on the same dedicated connection used by Drizzle, releases/discards it on success or failure, and prevents the two current service commands from racing. This depends on every migration invocation using the shared runner and the same database. PGlite does not validate real concurrent PostgreSQL sessions/advisory locking.
- Feedback account validation, `FOR UPDATE` account lock, prior-request lookup, rate-limit consumption, and encrypted insert occur in one transaction. Identical retries return the original receipt without consuming another slot; changed payload under the same account/request ID conflicts. `(user_id, request_id)` is also unique. An insertion failure rolls back cap consumption.
- Account deletion deletes the `users` row; feedback FK cascade removes report detail, HMAC, and receipt. The parent account lock serializes submission with deletion. Account-scoped receipts cannot read another account's report. The generic feedback rate-limit key is outside the FK cascade and ages out via existing operational cleanup; it contains no report detail.
